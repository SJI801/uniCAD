# 2026-10-11 — 修 WebGL 缓冲越界与内核加载噪音

## 用户报告（dev server 控制台）

```
WebGL: INVALID_VALUE: bufferSubData: buffer overflow   × 大量
unicad_kernel.js: using deprecated parameters for the initialization function
```

并且 `initKernel` 的加载栈出现 **4 次**（Workbench ×2、CanvasView ×2）。

## 三处根因

### 1. `bufferSubData` 越界 —— 每帧无条件 `bufferData`

旧 `GlRenderer.upload` 每帧对每个 buffer 调一次
`bufferData(target, elementCount * es, DYNAMIC_DRAW)`，把缓冲重新分配到
**恰好**本次写入量。

一旦驱动拒绝分配（显存不足 / 超过上限，核显共享显存尤其容易），
**`bufferData` 失败不会改变缓冲尺寸，它静默保持旧的小尺寸**，
紧随其后的 `bufferSubData` 就撞上 WebGL 自己的边界检查 →
`INVALID_VALUE: bufferSubData: buffer overflow`。

Chrome 对 WebGL 警告**不给 JS 调用栈**，所以从控制台完全看不出发生在哪次上传。

**修法**（`src/render/gl.ts`）：
- 新增 `bufferBytes: Map<WebGLBuffer, number>` 记录每个缓冲已分配字节数
- 改为**容量增长式**：仅当 `bytes > have` 时重新分配，几何级数增长
  （`max(bytes, have * 2, 1024)`）
- 分配后检查 `gl.getError()`，失败则清除容量记录并**跳过本次写入**
- `bytesPerElement` 改为**显式传参**，不再用 `instanceof Float32Array` 嗅探
  （嗅探错了会算错分配量，而症状是 GL 越界而非类型错误）
- `dispose()` 清空 map

副作用（正面）：每帧 `bufferData` 调用从 5–8 次降到 **≈0**。
实测 2997 次 `bufferSubData` 只触发 3 次重分配。

### 2. wasm-bindgen 弃用警告

glue 的 `__wbg_init` 支持两种入参：新式 `{ module_or_path }`、
旧式位置参数（会 `console.warn`）。改用
`pkg.default({ module_or_path: wasmUrl.default })`。

### 3. `initKernel` 重复加载

`Workbench` 和 `CanvasView` 各自调一次，StrictMode 双挂载再翻倍。
虽然 `if (mod) return mod` 能防重复初始化，但**并发调用时 `mod` 还是 null**，
会同时发起多次 fetch + instantiate。

**修法**：
- `initKernel` 加模块级 `loading: Promise` 缓存，并发调用共享同一个 promise
- `Workbench` 的调用改为"静默预热"（不记日志），状态与日志统一由
  `CanvasView` 负责 —— 否则每次加载打两遍同样的日志

## 顺带修掉的脆弱设计

`kernelReady` 原本由 `setKernelStatus` 内部
`text.startsWith('WASM')` 推断。**状态文本是给人看的显示文案，改一次措辞
就会静默关掉拾取 / 捕捉 / 测量**（这些功能都以 `isKernelReady()` 为守卫）。

改为独立的 `setKernelReady(boolean)` action，由 `CanvasView` 显式调用。

## 新增工具

**`scripts/probe-gl-overflow.mjs`**（`npm run verify:gl`）
在页面里挂钩 `bufferData` / `bufferSubData`，用
`getBufferParameter(BUFFER_SIZE)` 自己复算
「目标缓冲实际容量 vs 本次写入字节数」，命中时记录完整参数 + 调用栈。
同时统计两类调用次数，用来确认容量增长策略生效。

`--big` 参数模拟大窗口（2560×1440）+ 高分屏（DPR 2）+ 全选 + 缩放。

分配量恒 ≥ 写入量，分配失败则跳过写入。

# 「画布不显示」排查（第二轮）

用户报：**画布不显示**。前一轮修完 crash 与缓冲越界后，控制台已干净、
缓冲上传也全部执行，但画面上什么都没有。这轮挖出 **5 个叠加的渲染层 bug**。

## 根因 1：着色器 uniform 被 GLSL 优化掉

`LINE_VERT_SRC` 声明了 `uniform mat3 u_view` 却从未读取（顶点实际用
`u_viewRigid`），GLSL 直接把它删掉 → `getUniformLocation` 返回 **null**，
而 `gl.uniform*` 对 null 是**静默 no-op**。

更糟的是 `drawLines` 把**裁剪矩阵**喂给了 `u_viewRigid`，而后者按契约是
「模型 → CSS 像素」，shader 后面还要自己把像素转回 NDC。空间错配 →
所有顶点被压到一个角落。

**修法**：删掉 `u_viewRigid`，只留 `u_view` + `u_viewport`，在 shader 里
显式写清 `模型 → clip → CSS px → 偏移 → clip` 的往返。并加了
`GlRenderer.uniform(program, name)`：位置取不到就**构造期抛异常**，
把「静默空画布」变成带名字的启动错误。

## 根因 2：`buildLineBatch` 是覆盖而非追加

一帧调三次（实体 / 栅格 / 叠加层），每次从偏移 0 重写并重置顶点数 ——
**后一批把前一批整批擦掉**。所以实体被栅格覆盖、栅格又被叠加层覆盖，
最终只剩最后两批。

**修法**：改成追加语义（记录 `base` 游标，只上传新增切片，`bufferSubData`
带 `dstElementOffset`），`drawLines` 画完归零，每帧开头显式
`beginLineBatch()`。顺带把三次 draw call 合成一次。

## 根因 3：`LineTool` 永远提交不了

`commitRun()` 零调用者，私有 `chained` 恒为 false → 那个工具看着完全正常
（提示在走、橡皮筋在画、状态栏光标正确）却**一个图元都不产生**。

**修法**：改成「每点一次立即提交一条线段」，回车 / 右键 / `Esc` 结束，
`C` 补一条回到起点收口。逐段提交同时解决了「点完第二点看不到线」的体验问题。

## 根因 4：裁剪矩阵的 y 符号写反 → 整幅场景垂直镜像

`clipMatrixOf` 推导时把模型当成 y 向下，得到 `ndcY = -2*(y-cy)/(s*h)`；
正确是 **正号**（模型 y 向上，翻转在相机的 `worldToScreen` 里）。

症状：点左上到右下画的线，出现在左下到右上；示例图纸的圆弧（顶点 y=96）
画到了矩形**下方**。控制台零报错。

这个公式有**三份副本**（`Camera.clipMatrix`、`gl.ts:makeViewMatrix`、
`CanvasView` 内联），后两份从未被调用，唯一在用的那份符号写反。
**修法**：`camera.ts` 只留一个 `clipMatrixOf(view)`，另两处改为转发。

交互侧（`toWorld` / `store.screenToWorld` / `Camera.worldToScreen` /
`panBy`）全部是正确的 y 向上，所以这次只翻转渲染，没动交互。

## 根因 5：覆盖层的点尺寸是模型单位，渲染器当像素用

`snapMarker(p, kind, sizeModel)` 的契约是模型单位，`drawPoints` 却把它当
CSS 像素塞给 `gl_PointSize`。7 px 的夹点在 1:4.3 下只有 1.6 px（几乎不可见），
缩小视图时又会无限变大。顺带 `drawPoints` 有叠加点精灵堆叠与
「尺寸属性压根没在 VAO 里绑定」的问题。

**修法**：点精灵改 `gl_PointSize` + `u_dpr`，VAO 绑定 attrib 2，
片段着色器用 `gl_PointCoord` 削成圆点，尺寸统一为 CSS 像素
（`OverlayPoint.size` 契约已写清），只画 `points.length` 个点。

## 验证纪律升级

新增 `scripts/verify-canvas-pixels.mjs`（`npm run verify:pixels`）：

1. 自解 PNG 统计画布区域非背景像素占比与颜色种类；

   这是唯一能抓住「几何喂错空间」的断言；
3. 断言图元数确实 +1（无报错 ≠ 画对了）。

同时修掉三个「空跑通过」的检查：
- `verify:gl` 默认端口没人监听、`--big` 还被当成 URL → 改成取第一个非
  `--flag` 参数 + 可达性预检 + 「一次上传都没记录到」判失败；
- `verify:render` 的图元数正则 `/图元[\s\S]{0,40}?(\d+)/` 实际匹配的是
  「图元 / 1 图层」里的 **1** → 改成 `/图元\s+(\d+)/`，并加图元数断言；
- 三个脚本统一默认端口 5273（dev），连不上直接报错退出。

## 一个重要的误判教训

**不要靠肉眼看截图判断描边是否连续。** 截断后预览缩放显示时，1.4 px 宽的
斜线看着像虚线，轴对齐的长直线却不会 —— 很容易误判成「圆弧渲染断裂」。
用 `--runs` 量游程后确认圆弧是连续的（切线方向 17 px 跨度只缺 2 px）。

同样地：合成点击必须**按下 + 松开成对发送**，两次 `mousePressed` 之间不松开
会被浏览器合并，工具永远停在「指定下一点」。

# 追加：用户报「画的线粗细不均匀」—— 根因是四边形顶点布局错位

## 现象

曲线（圆/圆弧）被渲染成**虚线**，周期恰好等于细分弦长；直线看起来正常。
用户的原话是「粗细不均匀」。

## 排查路径（值得复用的顺序）

1. **先看放大图，不要看 100% 缩略图。** 给 `verify-canvas-pixels.mjs` 加了
   `--zoom=x,y,w,h,f`（自写 PNG 编码 + 最近邻放大 + 逐行亮游程）。5 倍下
   一眼看出圆是断的。
2. **沿法线量宽度。** 加了 `--ring=cx,cy,r`（环绕一圈测宽度分布）和
   `--probe=ax,ay,bx,by`（直线对照组）。
   - 圆环：min 0.005、45/720 采样点无墨、34 处谷、CV 50.8%；
   - 直线：min 1.27、0 点无墨。→ **只发生在曲线上，即接缝问题。**
   - 关键数字是「谷间距」：34 个谷、间距 10.5 px 弧长 = 细分弦长 10.7 px。
     **周期锁定在镶嵌上**，排除栅格（43 px）、虚线样式（10/6）等嫌疑。
3. **抓真实顶点流。** 加了 `--dump-verts`，在页面里挂钩 `bufferSubData`
   记录 pos/normal/side/width 四个窗口。这一步是决定性的：
   - 顶点数 = 522 = 87 段 × 6，**一段没漏**，弦长全是 2.5099 → 几何完整；
   - 于是问题只能在「每段 6 个顶点怎么摆」上。

## 根因

顶点布局原本写成两个取模表达式：

```ts
pos[vi*2]  = k % 3 === 0 ? x0 : x1;   // k: A B B A B B
side[vi]   = k % 2 === 0 ? -1 : 1;    // k: - + - + - +
```

两者在 `k = 5` 上矛盾：位置说是**终点**，侧向说是 **+1**，但终点的正侧
应该是 +1 而 `k%2` 给的是 +1 —— 位置和侧向的组合变成了
`(A-, B+, B-)` 与 `(A+, B-, B+)`，**两个三角形沿不同对角线剖分**，
并集少掉四边形**起始那一半**（面积刚好一半）。

于是每个梯形只画出了「后半边」，接缝处自然周期性断开。
直线之所以看不出来：单个线段的两半缺口都被同一段自身遮住；
而曲线上每段都紧邻下一段，缺口就裸露出来了。

## 修法

改成显式顶点表（`QUAD_AT_END` / `QUAD_SIDE`），两个三角形共用
`A- ↔ B+` 对角线：

| k | pos | side |
|---|---|---|
| 0 | A | -1 |
| 1 | B | +1 |
| 2 | B | -1 |
| 3 | A | +1 |
| 4 | B | +1 |
| 5 | A | -1 |

## 同时做的三件事

1. **斜接接头**：每顶点取相邻两段法线的角平分线，乘 `1/cos(θ/2)`（上限 4）。
   相邻梯形共用端边 → 无缺口、无重叠（有重叠就会 alpha 叠两次变黑）；
   直角处线宽不再被压窄 29%。
   **陷阱**：开放折线的首尾只有一个邻居，此时角平分线就是该段法线，
   不能再乘补偿系数 —— 否则每条线两端都是两倍宽（实测矩形边从 2 行
   亮像素变 3 行才发现）。
2. **解析抗锯齿**：片元用 `clamp((ext - |off|) / (2 * u_aa), 0, 1)` 算覆盖率，
   `u_aa = 0.5 / dpr`（半个设备像素）。之前完全依赖 MSAA，而 1.4 px 细线的
   表观粗细由亚像素相位决定 —— 沿曲线周期摆动 40%+。
3. **`resize()` 取整一致**：原本背板 `floor(592.6)=592`、CSS 保留 `592.6px`，
   浏览器把整块画布重采样一遍。实测 `canvas.width=592` vs `clientWidth=593`。

| 指标 | 修前 | 修后 |
|---|---|---|

| 圆环谷数量 | 34 | **0** |
| 圆环 CV | 50.8 % | 28.1 %（残余来自与其他图元交叉） |

Vite 在两次之间缓存了转换结果，于是页面跑的是「新常量 + 旧发射循环」，

# 顶部工具栏收拢（同日，第四轮）

## 需求

> 收拢顶部工具栏

## 做法

工具栏两档高度，最右端常驻 ▴/▾ 按钮或 `Ctrl+F1` 切换：

| 状态 | 高度 | 内容 |
|---|---|---|
| 展开 | 62px | 六个带标题分组（文件/交换/绘图/修改/视图/捕捉与追踪） |
| 收拢 | 34px | 单行：文件 ▾ 下拉 + 8 个纯图标工具 + 撤销/重做/删除 + 正交/极轴/捕捉/栅格 + 8 个捕捉 + 缩放范围 |

- 状态进 store（`ribbonCollapsed` + `setRibbonCollapsed` / `toggleRibbon`），
  写 `localStorage['unicad.ui.ribbonCollapsed']`。**不能放组件局部 state**：
  快捷键层也要翻它，且刷新必须记得住。
- 首次访问（无存储记录）时 `window.innerWidth < 1900` 直接给收拢态 ——
  展开态是 ≈1850px 控件，放不下。显式选择永远优先。
- 收拢态**一个控件都不少**：绘图工具缩成纯图标方格（`title` 保留名称+别名），
  三个文字分组折进 `文件 ▾` 下拉。约束/捕捉开关保留文字（图标猜不出来，
  点错会让后续标注静默跑偏）。

## 两个实现坑

**1. 收拢按钮必须 `position: sticky; right: 0`。** 展开态要横向滚动，
普通 flex 子项会跟着滚出屏幕 —— 唯一能把空间还回来的控件成了唯一够不到的那个。
sticky 贴滚动视口右缘，必须配不透明背景（否则控件从底下透出来）。

**2. 下拉必须是 `position: fixed` 的兄弟节点。** `.ribbon` 是 `overflow-x: auto`
滚动容器，放进去会被裁成 34px 高的缝。坐标取 `getBoundingClientRect()`。
菜单打开时 `Escape` 要 `stopPropagation`，否则全局快捷键层把同一个键读成
「取消当前命令」（`document` 捕获阶段能拦住 `window` 冒泡阶段）。

## 顺带修掉的既有缺陷

`.osnap-row` 原本 `flex-wrap: wrap`，而这条栏是**定高 62px + `overflow-y: hidden`**：
换行的第二行不是「挤」而是**看不见**，连组标题一起被裁。而且 wrap 让内容不再溢出，
`overflow-x: auto` 从不触发 —— 一个控件都不报错地消失。改为单行 + 横向滚动
（`.ribbon-group.grow` 从 `1 1 auto` 改 `0 0 auto`，让总宽如实反映内容）。

## 验证脚本（新）

`npm run verify:ribbon` —— 34 项断言，不碰像素（收拢是布局契约）：

- 让出高度精确 = 28px，且 `.canvas-host` 同步长高 28px（测 ResizeObserver）
- 画布 CSS 盒 = 容器高度；backing store = CSS 盒 × dpr
- 收拢后 11 个图标按钮 + 8 个工具 title + 14 项文案 + 8 个捕捉 title 全部在位
- 下拉 178×191 完整落在视口内、6 个菜单项文案齐
- 收拢/展开双向刷新持久化
- 展开态：组标题与按钮无纵向裁切、捕捉开关 `top` 值只有一个（单行）

**踩到的测试坑（值得记）**：第一版脚本断言「菜单开着时按 Escape 工具不变」——
但**前一步点工具按钮就已经把菜单关掉了**（外部点击），那次 Escape 压根没经过菜单，
断言恒真。补了「先重新打开菜单」的前置断言 + 一个**对照组**
（菜单关着时 Escape 应该退回选择工具）。**只写「不该发生的事」不够，
必须写一条能证明这条断言不是空转的对照。**

# 自动尺寸（同日，第五轮）

## 需求

> 显示自动尺寸

歧义大，问了一次。用户选：**绘制中 + 选中时实时显示**（纯屏幕提示，
不进文档、不参与撤销）。

## 关键发现：读数早就算好了，只是从来没人渲染

`PreviewGeometry.readout` 存在，每个工具都在算（`R = 21.350`、`长度 120.000`、
`距离 45.0  角度 26.57°`…），注释写着「给状态栏用」—— 而状态栏也没接。
`grep readout src/` 只有 tools.ts 自己。所以这个特性的一大半是**把已经存在的
数字显示出来**，而不是从零造。先 grep 再动手，省掉了一半工作。

## 架构

新增 `src/render/dims.ts`：

- **几何走模型坐标**，并进和网格/图元同一个 GPU 批次 → 高亮与标注都不触发重新镶嵌
- **文字走屏幕坐标 + DOM 层**：浏览器自己的光栅化器出的字比字形图集清晰得多
- `dims.ts` 是唯一同时产出「几何 + 文本」的模块，两个通道在这里汇合

`CanvasView` 里：

- `.dim-layer` 是个**空的** div（不能有 React 子元素），由渲染循环手工池化维护
- `syncDimLayer()`：`<span>` 池，不够就长、多了 `display:none`，只在真变了才碰
  `textContent` / CSS 变量。**每帧 setState 会让 800 行的组件每秒重渲染 60 次**
- 位置走 `--dx/--dy` 两个 CSS 变量，居中的 `translate(-50%,-50%)` 留在样式表
- 每帧取整到整数像素（亚像素位移会让文字每帧重新光栅化，糊成一团）

`overlay.ts` 的 `measurementLeader` **搬进了 dims.ts 并删掉** —— 它是唯一还要吐
文字的 overlay，留两处就是两份会各自漂移的实现。

## 四条判定规则

1. **模型法向 → 屏幕方向只翻 y**（模型 y 朝上、屏幕 y 朝下且两轴等比），
   所以是 `(nx, -ny)`。偏移距离与刻度长度一律按屏幕像素给、再乘 scale 换成模型
   单位 —— 标注是给眼睛看的，离图元的距离在任何缩放下都得一样。
2. **标签要 clamp 进视口**。否则边缘图元的标签被 `overflow:hidden` 裁掉半个数字，
   而「差一点就能看见」比不显示更抓狂。
3. **朝向看整批选中对象的包围盒中心**。单看一条边判断不出外侧（两侧完全对称），
   把选中的这批当成「这个图形」方向才定得下来。不做的话矩形左右竖边会把尺寸线
   画进内部压在圆上 —— 而每个数字本身都是对的，只有位置断言抓得住。
4. **`pointer-events: none`**，标注绝不能挡住拾取与拖拽。

上限 40 条（框选几百个时逐条标注只剩糊屏）。圆的半径线 offset=0 时不画起点
刻度（会正好落在圆心上糊成小星芒）。

## 收尾：像素脚本对尺寸标签的免疫

自动尺寸的标签是**真实 DOM 元素**，而 `Page.captureScreenshot` 会把 DOM 一起
合成进来 —— 标签一旦压在被测的圆环/直线剖面上，量出来的「描边宽度」其实是
标签的边框，症状会和「描边断了」一模一样。截图时恰好没有标签（既无选中也无
绘制中），但那是巧合不是保证。

`verify-canvas-pixels.mjs` 在 `Page.captureScreenshot` 之前加了一步把
`.dim-layer` 设成 `display: none` 再等两帧。改完重跑两项，数值与改动前**逐位
一致**（非背景 8.661%、亮点 740、bufferData 13 / bufferSubData 2976 /
skippedAfterAlloc 0；圆环与直线均 0 无墨点），确认这步没有扰动测量。

**教训归档**：凡是「给画面加了新图层」，就要问一句「它会不会被截图量化脚本
当成被测对象」。DOM 覆盖层和 WebGL 画布在截图里是同一个像素平面。

## 做了什么

需求一句话：「属性中任何参数都能修改」。原来面板里**整块「几何」都是只读**，
只有颜色和线宽可改 —— 那不是设计，是遗漏。

- 新增 `src/core/props.ts`：**表驱动的参数描述**。每个参数一行，自带
  `applyTo/applyValueTo/inheritFrom`。「能不能改」= 「这一行有没有 applyTo」，
  没写的必须显式声明 `kind: 'info'`，于是「新加参数忘了写 apply」和「忘了加进
  面板」都会立刻暴露。
- `applyTo` 的第一个参数是**当前实体**，不是渲染时捕获的那个。面板按一份快照
  渲染、按另一份快照提交（store 建撤销补丁时会重新读实体），闭包捕获渲染时的
  实体就会写回陈旧副本、把中间发生的改动悄悄回滚。
- 可改参数：图层/颜色/线型/线宽/名称 + 各类型全部几何量。派生量（直径、周长、
  面积、总长度、角度、扫掠角、弧长）**同样可改**，规则写在 tooltip 里：
  改长度→固定起点沿原方向移动终点；改角度→长度不变绕起点转；圆改直径/周长/
  面积→反解半径；圆弧改扫掠角→固定起始角（夹在 (0,360) 防退化）；改弧长→
  固定圆心角缩放半径；椭圆改面积→等比缩放两半轴；多段线改总长度→绕质心等比
  缩放；顶点数→结构参数，加则复制末点、减则丢尾（下限 2）。多段线**每个顶点**
  都有 X/Y 输入（上限 64 行）。
- 颜色/线型/线宽支持「随层」清除覆盖；随层时色块显示**实际生效**的图层色。
- 多选：列出通用参数（不含名称、不含几何），取值不一致的显示「多值」占位 /
  「（多个值）」选项，改一次应用到全部所选，**一条命令**、一次撤销回滚全部。
- 数值输入用 `type="text"` + 草稿态：改一次 = 撤销一步（不是每个字符一步），
  输入过程中不与几何打架（打 100 会先变成 1 再变成 10），Esc 撤销本次输入，
  上下箭头按 step 步进。

## 顺带修掉的既有 bug：线型是假的

`RenderStyle.dash` 算出来了但**渲染器从来不读** —— 图层表里那个「线型」下拉
点了没有任何反应。属性面板要正经暴露「线型」，就必须让它真的生效。

- 给线段着色器加两个顶点属性：`a_arc`（沿线的累计弧长，**CSS 像素**）与
  `a_dash`（`vec4 = (period, on0End, on1Start, on1End)`，见 `packDash`）。
  片元阶段按 `mod(arc, period)` 裁切，两段「实」区间足够表达全部六种图案。
- **不在 CPU 上把线切成小段**：斜接接头是在**未切分**的顶点序列上算的，先切
  就等于把每一段内部的接头变成两个平头端。着色器裁切让接头完全看不见图案。
- 虚线段端头用**距离场羽化**（`d/aa*0.5+0.5`）。硬 `step` 会让每个虚线端头成为
  逐**片元**的边，而 `discard` 是一次丢掉整个片元的所有采样点，MSAA 救不了 ——
  端头会明显锯齿。
- **删掉了一个我自己写的兜底**：原本有「周期 < 4px 就画实线」的分支，理由写的
  是「缩小后虚线退化成亚像素噪声」。写完才想明白这是错的：图案定义在屏幕像素、
  弧长也按屏幕像素传进去，所以渲染出来的周期**不随缩放变化**，那个分支永远走
  不到。留着它就是留一段没有输入能触达的代码 + 一段解释不存在机制的错误注释。
  改成在验证里断言「放大 2× 后周期不变」，这一条同时能区分「屏幕空间图案」和
  「模型空间图案」两种实现。

## 曲线修剪功能（TRIM）

用户澄清后确认：要的是**修剪**（trim），不是样条/贝塞尔。范围选「完整落地」。

### 内核 `kernel/src/trim.rs`（新建，约 450 行）

核心抽象：把目标图元归约成**一个标量参数 `u ∈ [0,1]`**（直线 t / 圆弧归一化扫掠角 /
圆 TAU / 多段线累计弧长）。交点是 `u` 上的点，排序后切成**区间**；点击落在哪个区间
就删哪个、**其余全留**。

按区间而不是「从 A 删到 B」是重复修剪能正常工作的原因：被三个边界切过的直线，
删掉一段后远处那几段还在。`victim_index` 让点击正好落在切点时归给**后面**那个区间，
否则会在两个结果间反复横跳。

- **椭圆明确不支持**，返回 `Unsupported`。剪掉的椭圆是「椭圆弧」，本项目没这种图元；
  悄悄退化成多段线会让类型变了、属性面板对不上、DXF 也导不回。宁可明说。
- `slice` 对 `Circle` 不做整圆防护 —— 整圆区间要求切点集为空，而那条路被
  `NoCuts` 提前挡住了。这个推理写在注释里，不是「忘了加」。
- FFI 侧 `trim_target` / `trim_preview` **都过滤掉「刀刃里有目标自己」**：目标与自身
  相交无穷多点，不挡就是碎成一地渣片。防御放在内核，因为唯一能触达它的是点击处理器。
- 预览让内核直接返回镶嵌好的顶点（`preview_points`），不在 TS 里重写一遍切片逻辑。

### 写这个时自己抓到的一个 bug

`locate()` 对多段线原本只返回 `cum[seg]`（所在线段的**起点**弧长）。但一个线段里
可能有**两个**切点，那样该线段会横跨多个区间 —— 每次点击都落在第一个切点之前的区间，
点线段中间会剪错东西。改成 `cum[seg] + 段内偏移`。

### 前端

- `src/core/trim.ts`（新建）：刀刃集合（所有可见图元，去掉目标）、把内核返回的
  wire pieces 变成**继承目标图层/线型/线宽/颜色**的实体（否则剪完会悄悄改色）、
  `trimCommand` 把「删目标 + 加剩下的段」组装成**同一条 Command**（分两条会让一次
  Ctrl+Z 只回滚一半）。顺带级联删除目标身上的约束。
- `TrimTool`（`src/tools/tools.ts`）：**自己拾取目标**，点击坐标只是提示（十字准线有捕捉，
  原始点会偏一点）。红色预览整条待删段。
- `ToolContext` 加 `pick()` 与 `viewScale()` 两个注入方法 —— 拾取要活文档 + 内核，
  让每个工具自己去 packScene 就会每个工具各打包一次整幅图。
- `PreviewGeometry.segments` 加可选 `color`；`UI_COLORS.cut = #ff5d5d`。
  **没有从 `render/style` import** —— `describeEntity` 当初就是**从那里搬出来的**，
  理由正是「工具反向依赖渲染层」，不能又引回来。
- 预览节流：move 事件是 16 ms 一tick，每 tick 一次 packScene + 内核往返。
  缓存上次的光标点，没动就跳过。点完必须 `force` 重算（文档变了，光标没动）。

### 状态

`npm run typecheck` 0 错误。**`cargo check` 没跑、`npm run wasm` 没跑** ——
`trim.rs` 一行都没编译过，wasm 里还没有 `trim_target`。README「验证状态 → 修剪」里
写了 11 条手动验证清单。

## 自动图元分解（以交点为基准）

用户需求一句话：「自动图元分解以交点为基准」= AutoCAD 的 break-at-intersection。
按「有选中就分解所选，没选中就分解整幅可见图元」实现（让它能当 DXF 导入后的一键清理）。

### 关键决定：**不写第二套参数化**

动手前先 grep，发现 `trim.rs` 里 `cut_params` + `slice` 已经是「按 u ∈[0,1] 参数区间
切分」的全部 machinery，分解要的**切点完全相同、子图元完全相同**，只有「丢掉被点的
那一段 vs 全留」这一处差别。所以：

- `trim.rs` 抽出 `cut_params_from_points(target, points)`，`cut_params` 改为
  「先用 `query::intersect` 收点，再调它」。
- 新模块 `kernel/src/split.rs` 只做 `locate → 排序 → slice → 全留`。
- `slice` / `cut_params` / `cut_params_from_points` 改成 `pub(crate)`。

**教训（值得反复用）**：看到两个功能像，就先确认它们的**切分**是不是同一件事。
两套参数化迟早会在某个退化输入上给出不同切点，而这种 bug 只在用户画了张特定图时出现。

### FFI 只求交一次

`split_scene(encoded, counts, tol, max_seg)` 一次调用处理整幅图：每个**无序对**求交
一次，把交点同时 push 给两侧的 `crossings[i]` / `crossings[j]`，然后逐实体调
`split_at_points`。若让每个目标自己重算 crossings，每个交点会被算两次，且多一轮遍历。
外面还套了 `bounds().expanded(tol).intersects()` 粗筛 —— `intersect` 对混合类型会退化成
「双方镶嵌化成线段再两两求交」，大图纸上逐对都算很贵。

返回 `[groups, (entityIndex, count, ...prims) × groups]`；**没被切开的实体不出现**，
所以空数组 = 「整幅图没有交点」，这是个真答案而不是失败。

### 差点写第二个解析器（自己抓到的）

先写了 `skipGroup()` 想跳过不关心的分组，理由是「多段线的 wire 格式变长、
点数不存、不能靠算术跳过」。写完就意识到这是在写**第二个 wire 解析器**，它和
`decodePieces` 迟早会漂。改成让解码器自己报游标：

- `trim.ts` 加 `decodePieceRun(buf, start, count, target): { pieces, next }`
- `decodePieces` 变成它的薄包装（修剪只需要 pieces）
- `split.ts` 用 `decodePieceRun` 拿 `next` 推进游标

**通则**：wire 格式是变长时，任何「跳过 N 字节」的算术都是第二份解析器。
让解码方回报位置，而不是让调用方猜长度。

### 前端

- `src/core/split.ts`（新建）：`splitTargets`（选中有则筛选中，否则全部可见；隐藏/
  冻结图层一律排除）、`splitEntities`（打包**整幅可见图**当场景，因为目标要被
  不参与分解的图元切）、`splitCommand`（**倒序**删原实体 → 级联删约束 → 加新段，
  全部同一条 Command）。
- store `splitAtIntersections()`：分解后**自动选中新生成的段**（原 id 已失效）。
- Ribbon「修改」分组加「交点分解」；命令行 `EX` / `EXPLODE` / `SPLIT`。
- `RIBBON_AUTO_COLLAPSE_BELOW` 2210 → **2280**（第三次因加控件上调）。
- 椭圆单独选中时给**专属提示**，不回「没有交点」—— 用户按了按钮就该知道为什么。
- README 加「交点分解（EX）」节 + 快捷键 + 目录结构 + 「验证状态」12 条手动清单。

## 修「修剪剪错段」—— 预览与点击各拾取一次

用户反馈：「修剪应该以交点为界限」+ 现象是**剪错了段**、**多种图元都有**。

### 先查证，别先改

「以交点为界」听起来像切点来源错了，于是先查求交：
`geom.rs:105 LineSeg::intersect` 要求 `0 ≤ t,u ≤ 1`，`geom.rs:191
intersect_segment` 卡 `-1e-9..=1.0+1e-9` —— **都是查范围的**，延长线交点进不来。
`cut_params` 除了端点 `0/1` 只塞 `query::intersect` 的返回值。**切点本来就只来自交点。**
所以问题不在切点，在切点之后。问了一句现象（剪错段 / 段数不对 / 剪不动 / 形状错），
得到「剪错了段」。

### 真根因：预览与点击**各调了一次 `ctx.pick`**

`TrimTool.refreshHover`（拾取 → 画红色预览）和 `TrimTool.cut`（**重新**拾取 →
剪）是两次独立拾取。十字交叉处两条线都落在 `pickAperturePx` 孔径内，`pick` 回的是
「离光标最近的那个」，于是悬停与点击之间差零点几个像素就可能拿到**另一条线**：
**红色预览画的和实际被剪的不是同一个东西。**

这也解释了为什么「多种图元都有」—— 与图元类型无关，取决于**离交点多近**，
而交点正是修剪发生的地方。

**修法**：新增私有字段 `hoverTarget: EntityId | null`，`refreshHover` 拾到谁就记谁，
`cut()` **优先用它**，只在它已不存在于文档时（撤销 / 文档重载）才回退到重新拾取。
所有清空 `hoverPieces` 的地方（`activate` / `cancel` / Esc·右键 / 拾取失败）同步清
`hoverTarget`，免得残留的目标活得比它的预览久。

### 通则（值得写进铁律）

**破坏性工具的「预览对象」与「作用对象」必须是同一个，且由预览那一步决定。**
凡是「悬停时算一次、点击时再算一次」的地方，两次计算只要输入有任何抖动就会指向
不同对象 —— 而用户唯一的判断依据（高亮）只反映其中一次。工具只能有一个「当前目标」，
存在字段里，点击时读它。

顺带一个仍然成立的判断：**听到「X 应该以 Y 为界」先查 Y 是不是本来就成立。**
这次若直接动手改切点来源，会改错地方 —— 真问题在拾取，不在几何。

### 截图复盘：只修实体级还不够，位置也要一致

用户发截图：横线 + 半圆弧交于交点1/交点2，红色标注中间段「应该被剪掉的线」。
顺着 hoverTarget 修复往下查，发现**只修了一半**：

- **实体级**：`cut` 读 `hoverTarget` ✅
- **段级**：预览在 `hoverAt`（上次 16ms 节流 move 点）算，`cut` 却把**点击落点**
  传给 `trimEntity`。内核 `trim` / `preview_span` 用的是同一个 `victim_index`
  （选段逻辑本身一致），但**喂的坐标不同** —— 点击点只要落在交点另一侧
  （快速移动时最后一次 move 可比点击早十几毫秒、差几十像素），内核就选中隔壁区间：
  **红的画在中间段，剪掉的是旁边那段。**

**修法**：`cut()` 改为沿 `hoverAt` 剪（`at ?? point`，回退路径才用落点）。
**预览画哪，剪的就是哪** —— 位置和实体一起锁定。`hoverAt` 的清空点上一轮已与
`hoverTarget` 同步，生命周期一致，不用再动。

铁律补充一句：破坏性工具锁的不只是「哪个对象」，还有「对象上的哪个位置」——
预览那次计算的**全部输入**（实体 + 坐标）都要在点击时复用，任何一次重算都是
第二次机会让预览与动作分叉。`tsc` 0 错误；Rust 侧仍未编译，运行时未验证。
